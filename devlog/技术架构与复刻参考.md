# Anime Hair Studio — 技术架构分析 & 复刻 DCC 参考

> 整理日期：2026-08-07 ｜ 对象版本：0.1.4（本地 fork：0.1.4-Sintaka.N）
> 用途：梳理本项目（网页端动画发片制作 App）的整体结构、前后端技术栈，以及后续复刻一个自研 DCC 时可以参考/借鉴的地方。

## 1. 项目定位

- **是什么**：一个**纯网页端**的动画头发/发片建模工具（web-based hair-sheet / hair-styling app）。直接在浏览器里绘制、雕刻、编织 strands / clumps / braids / panels，导出 `.ahs`、`.obj`、`.usda`。
- **原作者**：Ludetools（LuDe），仓库 github.com/Ludetools/Animehairstudio。
- **许可**：ANIME HAIR STUDIO SOURCE-AVAILABLE LICENSE v1.2（source-available，**非开源**；个人/非商业可用，商用需作者书面许可；保留 LICENSE 与捐赠链接）。
- **本地 fork**：`Sintaka` 分支在 main 基础上做持续本地适配（简体中文、自定义笔刷、Houdini 导航、快捷保存/导出等），详见 `devlog/README.md`。

## 2. 总体架构（核心结论）

**这是一个"零后端、零构建、零框架"的纯前端单页应用（SPA）+ WebGL。**

| 维度 | 结论 |
|---|---|
| 前端框架 | 无（不用 React/Vue/Svelte），原生 JavaScript ES Modules + 直接 DOM 操作 |
| 3D 渲染 | Three.js r165（WebGL），CDN 加载 |
| 构建/打包 | **完全没有**：无 webpack/vite/rollup，无 node_modules，无编译步骤 |
| 后端 | **没有传统后端**。唯一服务端是本地静态文件服务器（python http.server）|
| 持久化 | 浏览器侧：File System Access API + IndexedDB + localStorage + 下载回退 |
| 运行方式 | 起一个静态服务器打开 index.html（file:// 不行，模块/CORS 受限）|

一句话：**一个由 HTML + CSS + 原生 JS + Three.js 组成的、改完刷新就能跑的 3D 编辑器**。这正是"轻量、快迭代、适合 vibe coding"的核心来源——没有构建链，改一行保存、刷新浏览器即生效。

## 4. 技术栈清单

- **语言**：HTML5 + CSS3 + 原生 JavaScript（ES2020+，ES Modules）。
- **3D**：Three.js `0.165.0`，通过 **import map** 指向 unpkg CDN：

  ```html
  <script type="importmap">
    { "imports": {
        "three": "https://unpkg.com/three@0.165.0/build/three.module.js",
        "three/addons/": "https://unpkg.com/three@0.165.0/examples/jsm/"
    } }
  </script>
  ```

  用到 OrbitControls / TransformControls / OBJLoader / BufferGeometryUtils。
- **浏览器 API**：
  - File System Access API（showOpenFilePicker / showSaveFilePicker / DataTransferItem.getAsFileSystemHandle）→ 真实读写本地文件；
  - IndexedDB → 最近项目缓存；
  - localStorage → 偏好设置；
  - Blob + URL.createObjectURL → 下载回退；
  - crypto.randomUUID → 对象 id。
- **后端/服务**：无。可选的 dev-only"本地保存"通过 POST 到 `127.0.0.1:5173|5174/api/save-project`（由外部本地小服务提供，不在本仓库；日常保存走 File System Access API）。
- **模块化**：浏览器原生 ESM；`modules/package.json` 里 `{"type":"module"}` 仅为 Node 工具链识别用。
- **缓存策略**：所有 import 都带手动版本号（如 `./app.js?v=20260807-45`、`curve-math.js?v=20260805-2`），改文件后手动 +1 强制浏览器刷新——没有构建工具做 hash 注入。

## 5. 运行时数据模型（理解本项目的关键）

### 5.1 场景对象：lock（发片/发束/面板的统称）
每个 lock 大致包含：
- **标识**：`id`（UUID）、`name`、`scalpRegion`、`group/layer`、`materialId`
- **几何**：`points[]`（引导线控制点）、`pointTwists[]`、`pointWidths[]`、`width/depth`
- **拓扑**：`radialSegments`、`lengthSegments`、`dynamicDensity`、`twistDensity`
- **形状曲线**：`taperCurve` / `depthCurve`（+ secondary）——控制剖面宽度/深度沿曲线变化
- **类型**：`geometryType`（strand / braid / poly / surface / curve-surface）
- **标志**：`locked`、`mirror` 配对、`liveSurfaceGuide`、procedural 系列标志

### 5.2 其他场景数据
- **guides**：scalp guide / curve-lattice guide / capsule guide（头发生长引导与参考几何）
- **referenceImages**：2D overlay / 3D plane 参考图（.ahs 内嵌 base64）
- **hairMaterials**：自定义材质（标准/各向异性/动漫风格参数）
- **选择状态**：selectedId、selectedStrandIds、选择集、点选择等

### 5.3 项目文件 .ahs（本质是一个 JSON）

```json
{
  "format": "anime-hair-studio-project",
  "version": 1,
  "application": "Anime Hair Studio",
  "metadata": { "name", "savedAt", "strandCount", ... },
  "headAsset": {...}, "scalpGuideAsset": {...},
  "state": { "locks":[...], "guides":[...], "hairMaterials":[...],
             "referenceImages":[...], "visibleStrandRegions":[...], ... }
}
```

=> **整个场景 = 一个可序列化 JSON**，这是"外部接口友好"的根基（任何工具只要能读写 JSON 就能桥接）。

## 6. 关键子系统与工程模式

### 6.1 撤销/重做 = 全量快照
- `snapshotState()` 把整个场景状态序列化成纯对象 → `pushUndoState()` 入栈（有界 60 步）→ `restoreState()` 重建场景。
- 优点：实现极简、数据驱动；缺点：大场景内存占用高。
- **借鉴**：对 DCC 原型阶段很实用；正式做可换成 command 模式/增量 diff。

### 6.2 雕刻笔刷 = "单一遮罩装配 + 单一数据管线"
- 入口 `beginSculptMoveStroke` → `sculptBrushUnits()`（唯一 mask 装配器：可编辑/可见/可雕半空间/选择集/镜像配对）→ `applySculptMoveStrokeSample`（按笔刷分支执行）→ 统一写回 `syncLockFromCurve → 镜像同步 → 几何更新队列`。
- **借鉴**：这是一个非常好的"工具系统"样板——所有工具走同一数据管线，新增工具只需加分支，不重复写遮罩判断（本项目 devlog 明确要求：新增修改型笔刷不做独立 mask）。

### 6.3 UI = 传统 DCC 式（菜单/面板/对话框）+ 少量现代增强
- 顶部菜单（File/Edit/Curves/...）、左侧 outliner、右侧属性面板、中间 3D 视口；
- 浮动面板（Strand Profile / Width·Depth Curve）：可拖动、右下角缩放、右缘吸附属性面板（本地增强）；
- Radial 菜单（空格键）、快捷键面板、偏好设置对话框、Patch Notes 对话框；
- 全部 DOM + CSS，无虚拟 DOM。

### 6.4 本地化
- `SUPPORTED_LANGUAGES = en/ja/zh`；`translateUiString` 按语言词典分发，未收录回退英文；`createDocumentLocalizer` 遍历 DOM 文本/属性替换。
- **借鉴**：无需 i18n 框架，一套字典 + DOM 遍历即可。

### 6.5 导入导出
- 导入：`.ahs` 项目、OBJ（头模/全身/自定义 scalp）、参考图（2D/3D）；
- 导出：`.ahs`、OBJ（网格+中心曲线 polyline）、USDA（网格+曲线+bones/weights 骨架）；
- 全部自研（无第三方导出库）。

### 6.6 快迭代工程实践（vibe coding 友好）
- 无构建、无类型、无单测、无 LSP 项目配置（纯文本）；
- 改完刷新即生效；import 手动版本号 +1 防缓存；
- 大函数 + 清晰命名 + devlog 记录改动标注 → AI 协作时"读 devlog 就能接上下文"。

## 7. 风险与注意点

- **许可**：source-available，非开源，商用/再分发受限；复刻时**不要直接搬代码**，应学架构与思路。
- **单体体积**：app.js 1.6MB/3.6 万行，可维护性差；新项目建议一开始就按子系统拆分。
- **无类型/无测试**：重构风险高；建议新 DCC 用 TypeScript + 少量核心测试。
- **CDN 依赖**：three.js 走 unpkg，离线需本地 vendor。
- **浏览器 API 差异**：File System Access / getAsFileSystemHandle 仅 Chromium 系；Firefox 只能下载回退。
- **性能**：全量快照撤销 + 直接 DOM，场景很大时会吃力。

## 8. 复刻 DCC 的参考价值（结合你的需求）

### 8.1 这个项目"值得抄"的部分
1. **零构建 + 纯文本 = 极致迭代**：改保存→刷新→看到效果。这是 vibe coding 最舒服的形态，比 Houdini 的 HDA 重编译 / Python 进程重启快几个数量级。
2. **浏览器天然开放**：DOM、事件、WebSocket、fetch、Worker 全开放。**没有 Houdini 那种 private handle / 私有节点限制**——你完全可以自己写 gizmo、自己暴露任何数据给任何节点/脚本/外部程序。
3. **数据驱动 + JSON 项目文件**：场景即 JSON，撤销/重做/序列化/外部桥接全部围绕数据做。外部接口（MCP、LiveLink、DCC 桥）本质就是"读写这份 JSON + 事件通知"。
4. **工具系统样板（单一遮罩 + 单一管线）**：把"编辑工具"做成数据管线的分支，而不是每个工具各写一套——长期可维护，也方便做成可插拔。
5. **Three.js 视口 + 自绘叠加**：曲线/控制点/参考图/裁剪平面全在 WebGL 上自由画，视口适配完全由你控制（对比 Houdini viewport 适配差）。
6. **本地化/偏好/最近项目等"周边"**：都是几十行的小模块，随手可搬思路。

### 8.2 对照你提到的工具
| 工具 | 痛点 | 本项目/Web 路线的对应解 |
|---|---|---|
| Houdini | 节点/SOP 网络好用，但 HDA 是 C++ 重活、viewport 适配烂、handle 私有 | Web 里可以自建"节点图 UI"（用 HTML/SVG/canvas 画连线）；每个节点=一个纯函数管线；所有 handle/gizmo 自己写、随意开放 |
| Blender | 交互"怪"、Python API 与 UI 割裂 | Web 完全自定交互与数据绑定，无历史包袱 |
| ComfyUI | 节点图好但界面难用 | 节点图 + 传统 DCC 式面板/属性编辑器结合（本项目 UI 就是这套）|
| Zeno | 项目已烂 | 可挖其"核心算法遗产"（SOP 式数据流/解算思路），用 Web 重新实现 |

### 8.3 如果要复刻一个"轻量 DCC"，建议的架构起点
- **渲染**：Three.js（或 Three + 后期）自绘视口；数据与渲染分离（场景模型 = 纯 JSON，Three 只做视图）。
- **节点图（SOP 类似物）**：节点 = 纯函数（输入数据→输出数据），UI 用 DOM/SVG 画图；执行用 DAG 拓扑序；这样天然可缓存、可撤销、可外部驱动。
- **工具系统**：抄"单一 mask 装配 + 单一管线"，每个工具是一个策略分支。
- **撤销**：原型用全量快照，正式做 command 模式。
- **外部接口**：
  - **MCP**：把"打开/保存/导出/读取场景/执行节点"暴露成 MCP 工具，AI 直接操作 DCC；
  - **LiveLink / bridge**：浏览器 WebSocket/HTTP/本地文件监听，把动画数据（曲线/网格/参数）实时推给 UE/其他 DCC；
  - **协议**：全部基于 JSON 场景 + 增量事件（谁改了什么），好对接。
- **迭代工具链**：保持无构建或引入极轻量 dev server（Vite 也行）；加 TypeScript 提升可维护性。

### 8.4 可以立刻从本仓库"抄思路"的最小集合
1. `modules/curve-math.js` 的曲线采样/混合/twist 处理（纯函数，可平移成你想要的数学库）。
2. 雕刻笔刷的 mask 装配 + 分支管线。
3. 快照式撤销 + 场景 JSON 序列化。
4. import map + CDN 加载 three 的零构建姿势。
5. devlog 式的"改动标注 + 持续修改清单"协作流程（对 AI 协作极有用）。

## 9. 结论

本项目证明了：**一个功能完整的 3D 建模工具可以用"HTML + CSS + 原生 JS + Three.js + 浏览器文件 API"在零构建、零后端的情况下做出来**，并且迭代速度、外部可对接性（JSON 数据 + 开放 Web 接口）远好于传统 C++ DCC 插件开发。

如果你要复刻一个自研 DCC：
- **保留**：零构建/快刷新、JSON 数据驱动、Three 视口、单一数据管线的工具系统、快照撤销；
- **补强**：TypeScript、节点图（SOP 类似物）、命令式撤销、增量 diff、MCP/LiveLink bridge、本地 vendor 依赖；
- **避开**：单文件超大 monolith、无类型无测试、CDN 运行时依赖（离线场景）。

> 参考：项目本地 fork 的 `devlog/README.md` 记录了开发规范、JS 改动标注与"持续修改功能"清单（每次 main 更新后要优先同步哪些本地功能）。

## 10. 技术栈的 API 限制与弊端

### 10.1 浏览器安全沙箱（最根本的约束）
- **本地文件系统**：无法访问任意路径；只有用户显式授权（File System Access 选择器/权限提示）才能读写，且无法后台静默读写；拖入的文件只有只读 File 对象（拿不到可写 handle，Chromium 的 getAsFileSystemHandle 例外）。
- **网络**：没有原生 TCP/UDP socket；只能用 fetch / WebSocket / WebTransport / WebRTC；跨域受 CORS 限制；**从部署的 https 页面访问 localhost 会触发 Private Network Access 预检**（本地桥需要本地服务响应 Access-Control-Allow-Private-Network）。
- **进程/系统调用**：不能 spawn 子进程、不能加载本机 DLL / 调 Python 解释器；集成 C++/Python 必须走 WASM 或本地桥。
- **线程**：主线程单线程 + GC；多线程只能 Web Worker + SharedArrayBuffer，且 SAB 需要跨源隔离（COOP/COEP 响应头）。
- **窗口/OS 集成**：标签页不是原生窗口（无独立任务栏窗口、无系统级菜单/托盘、无全局快捷键）；多文档/浮动窗口要自己模拟。
- **生命周期**：标签页可被后台节流/休眠/回收；页面关闭即进程结束，无后台常驻。
- **持久化配额**：localStorage 约 5–10MB；IndexedDB 更大但非无限；隐私模式/无痕/不同浏览器数据互相隔离。
- **输入设备**：数位板压感/倾斜（PointerEvent.pressure/tilt）支持依赖浏览器与驱动，不是所有设备都能用；中键/侧键/多显示器/全局热键受限。

### 10.2 平台/浏览器兼容
- File System Access、getAsFileSystemHandle、WebGPU 等**仅 Chromium 系**；Firefox/Safari 只能回退到下载/本地服务器方案。
- WebGL 2 在部分旧硬件/驱动上有兼容问题；WebGPU 尚未普及。
- import map + ESM 需现代浏览器（基本已是基线，但旧浏览器仍需 polyfill/打包）。

### 10.3 工程/可维护性（结合本项目）
- 无类型系统、无测试、无构建 —— 迭代快，但大规模重构风险高、回归难发现。
- CDN 依赖（three.js）离线不可用；手动 ?v= 缓存号容易漏改导致"改了不生效"。
- 单文件 app.js（1.6MB / 3.6 万行）可维护性差，模块化虽有但主文件仍过大。
- 无插件/扩展标准：浏览器没有 DCC 那种官方插件 API，要做插件体系得自己设计（动态 import / iframe / worker 模拟）。

### 10.4 渲染/性能
- UI 与渲染同线程，复杂场景卡顿需 worker + 离屏渲染拆分。
- 全量快照撤销在场景很大时内存/耗时高。
- 大量几何体需要 typed array / instancing / LOD，纯 JS 遍历慢。

## 11. 对接已有 C++ 编译库 / Python 库的集成能力

### 11.1 C++（或 Rust）→ 浏览器
| 方式 | 说明 | 适用 |
|---|---|---|
| WebAssembly（Emscripten/clang） | 把 C++ 编译成 .wasm，性能接近原生；浮点基本持平 | 计算密集核心：网格/几何/解算/数学库 |
| WASM + 多线程 | wasm threads + SharedArrayBuffer + COOP/COEP | 并行算法 |
| WebGPU/WebGL compute | shader 级并行 | 粒子/大规模网格 |
| 本地桥（见 11.3） | 不编译，直接调用本机 DLL/进程 | 已有二进制、难移植的库 |

> 注意：WASM 在沙箱内无系统调用/文件/网络，I/O 要走浏览器 API；内存需要手动管理（或用 Emscripten 辅助）。适合"把核心算法遗产（如 Zeno 的 SOP 数据流）抽成库编译 WASM，JS 只做编排与渲染"。

### 11.2 Python → 浏览器
| 方式 | 说明 | 适用 |
|---|---|---|
| Pyodide（CPython→WASM） | 浏览器里直接跑 Python，可装纯 Python wheel（numpy 等） | 把 Python 当"脚本层"，纯逻辑/胶水 |
| 本地 Python 守护进程（推荐） | 浏览器 ↔ 本地 Python（FastAPI/WebSocket），Python 调 C++/原生库 | 生产形态：Python 大前端 + 原生后端 |
| Tauri/Electron 壳 | 桌面壳里 spawn python 进程 / require 原生模块（napi/ffi）调 C++ DLL | 打包成桌面应用 |

> Pyodide 局限：性能一般、C 扩展包受限（需要专门 wheel）、并发弱；适合脚本/胶水，不适合性能核心。

### 11.3 本地桥（最现实的组合拳）
- **WebSocket**（浏览器 ↔ ws://127.0.0.1:端口）：双向、低延迟、可推事件；浏览器前端与本地 Python/C++ 进程互发 JSON/二进制。
- **本地 HTTP/SSE**：fetch 调用 + Server-Sent Events 推送（单向更简单）。
- **文件监听桥**：写 JSON/缓存文件 + 轮询/文件事件（LiveLink 思路），零协议成本、延迟较高。
- **私有网络预检**：从 https 页面访问 localhost 需本地服务响应 Access-Control-Allow-Private-Network: true。

> 本项目已有先例：dev-only 的 POST /api/save-project（fetch 到 127.0.0.1:5173/5174）。把它升级为通用 WebSocket/HTTP API，即可成为"浏览器 ↔ 本地 Python"的标准桥。

## 12. Python 作为通用语言（DCC 大前端）的定位

### 12.1 为什么
Houdini（hython）、Blender（bpy）、Maya（maya.cmds）、Nuke、Substance、UE 编辑器脚本……几乎所有 DCC 都以 Python 作为脚本化/自动化"大前端"。复刻一个 DCC，对外暴露的脚本语言**应该就是 Python**，否则生态、资产流程、工具脚本全都要重造。

### 12.2 在一个 Web DCC 里落地"Python 大前端"
- **Python = 控制总线**：本地 Python 进程持有场景/操作 API（open / save / export / query / execute / node graph）；浏览器前端通过 WebSocket/HTTP 调用；Houdini/Blender/Maya 也能通过 Python 连同一总线 → 一个 Python 脚本同时驱动本 DCC 与其它 DCC。
- **场景数据双端一致**：场景保持纯 JSON（本项目已是）；Python 端与浏览器端围绕同一份模型工作；Python 改 → 事件推送 → 浏览器刷新视图；浏览器改 → 事件推送 → Python 更新。
- **节点图（SOP 类似物）**：节点 = 可序列化描述（type / params / connections）；执行器可跑在 Python（调 C++ 库 / 现有算法）或 WASM（内嵌计算）；Python 同时充当节点脚本语言。
- **MCP 集成**：本地 Python 进程本身做成 MCP server，把 open/save/export/query/execute node 暴露给 AI；浏览器前端也可内置 MCP client 或经本地桥调用 → AI 用自然语言操作 DCC。
- **LiveLink / bridge**：Python 端写 bridge（UE LiveLink、FBX/ABC 导出、OSC/WebSocket 推送），浏览器端只推 JSON 事件，不关心协议细节。

### 12.3 代价与风险
- 需要本地 Python 环境（解释器 + 依赖），部署复杂度上升。
- JS ↔ Python 跨语言边界需清晰协议（JSON-RPC / 消息 schema / 错误处理）。
- 性能关键路径仍在 WASM/原生，Python 只做编排，避免把 Python 写进热循环。

### 12.4 渐进式落点（针对本项目）
1. **阶段 1（纯前端，现状）**：维持零构建；可选把 curve-math / 笔刷核心编译成 WASM。
2. **阶段 2（本地 Python 桥）**：加本地 Python 守护进程（FastAPI + WebSocket），提供 open/save/export/query/execute；把 dev-only /api/save-project 升级为通用 API。
3. **阶段 3（Python 大前端 + 节点图）**：以 JSON 场景为中心，Python 端实现 node graph 执行器与脚本 API，浏览器端实现节点图 UI（DOM/SVG）；对外暴露 MCP server 与 DCC 桥。

> 一句话：**浏览器负责 UI/渲染/交互，WASM 负责性能内核，Python 负责脚本、自动化、节点图与对外桥接**——三者组合即可覆盖"轻量前端 + 快迭代 + 生态兼容（Python）+ 外部接口（MCP/LiveLink）"的全部诉求。
