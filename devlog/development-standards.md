## 开发规范 / Development guidelines

> 后续所有改动遵循以下原则：

- **实现最简化，不是记录最简化**：控制流与抽象层次能简单就不复杂，避免过度设计；但**不以删注释换简洁**。
- **注释写不变式，不写复述**：禁止复述代码在做什么（`// 加一` 类）；**必须**为以下四类写注释并给出理由——① 跨文件必须同规则的推导（列出全部同步点）；② 取整/钳位/边界的选择理由（为什么 floor 不是 round/ceil）；③ 数据所处坐标空间（authored / rest / 物化）；④ 刻意不改的东西及原因（如 `tipCaptureWeightAt`）。此类注释视为**契约**，重构时随代码一起更新，不得单独删除。
- **尽量使用已有的预设、开源库**：优先复用项目内预设与成熟开源库，避免重复造轮子。
- **减少手搓半成品**：少写自制的半成品实现，需要能力时优先引入成熟方案。
- **提交节奏（2026-08-19 用户明确，覆盖此前「等用户叫」的做法）**：**每一轮独立对话的修改完成后，就直接 commit 到 `DHS/develop`**，不必等用户指示——dev 分支的提交是 agent 的常规职责，且**每轮都要 bump 版本号**（`APP_VERSION` + `index.html` 两处入口缓存号 + `dom-contract` 的冻结断言，三者必须同步，见「版本/缓存号」条）。**`branch-deployment`（deployment 分支）是唯一例外**：只有用户**手动要求「更新 deployment」时**才可切过去 merge 并 push origin；agent 不得自行切换、合并或推送该分支。推论：dev 分支上不应长期积压未提交的工作树——若出现（如连续几轮只改不提交），后补时应在提交信息里**逐条列出所涵盖的版本区间**，因为文件已是终态、无法可靠地拆回各轮的中间状态。
- **分支管理（2026-08-17 起，统一 dev 分支）**：统一开发分支 **`DHS/develop`**（自 upstream/main d3358f6 起线性历史，承接全部本地适配）；日常开发与 bug 修复直接在该分支提交（节奏见上条）；大更改按需开临时 feature 分支（命名 `feat/<描述>`），完成后 merge 回 `DHS/develop` 并**立即删除**临时分支（用后即清，不再长期保留「版本号-操作」类分支）；发布时把 `DHS/develop` fast-forward/merge 进 `branch-deployment`（deployment 分支）并推送 origin；禁止直接 merge main（main=上游镜像，上游更新按功能移植，见下条）；历史分支（0.2.5x–0.2.6x、codex/*、v0.1.4-*）已于 0.2.81 整理：其提交已全部包含在 DHS/develop，仅 4 个已被替代的实验提交（0.2.58 的 tipScale 实验 2 个、codex/bangs-triangle-fix 的任务分支规范文档、v0.1.4-Twist-Fix 的 0.2.43 旧实现）记录后随分支删除。

- **main 上游更新移植（不 merge）**：main 上游更新一律**分析后按功能移植**，禁止对 main 做简单 `git merge`/`rebase`——本地已按域重构（`modules/<domain>/` 分域 + `app.js` 编排层），与 main 的扁平 `modules/*.js` + 大 app.js 正交，直接合并只会产生大范围冲突。流程：先读 main diff 弄清每个功能/bug 修复的**实现方式与依赖**，再逐功能判断四类处置——①可直接移植（新增模块/纯函数/自包含逻辑）；②需在本地架构上重新接线（功能重叠）；③本地已实现（标 `deprecated` 并删本地实现）；④本地已用不同方案解决（跳过，仅做决策记录）。**bug 修复必须先查本地是否已有/已用别法修复**，再决定是否移植；评估与移植结论写入 `devlog/main-sync-conflicts.md`。
- **按下标存储的创作数据必须有重映射函数**（0.2.117 教训，已复发过）：任何以「下标 = 身份」存储的 authored 数组（`lock.splitBones`、`lock.strandSplitBones` 等按段下标存 spread/曲线/tip 的结构），若其索引对象会被**重新划分**（增删 zipper 改变段数、loop 数改变链长），**必须**提供纯函数形式的插入/删除重映射（参照 `bone-model.js` 的 `remapSegmentBonesOnInsert`/`remapSegmentBonesOnDelete`/`cloneSegmentBone`/`resolveMergeSurvivor`），且**所有**增删路径统一走「先按身份重映射 → 再改划分数组 → materialize 双写 → 清理悬空选择」四步，禁止只改划分数组。派生字段（`name`/`parentParam` 等）克隆时置 null，交由 normalize 按**新**边界重派生，不得继承旧值。同批补两个测试：① 错位回归（断言重映射后的 delta **序列**，而非仅长度）；② 深克隆不别名。
- **一条推导规则只准有一个定义点**（0.2.118/0.2.119 教训，已复发过）：凡同一个几何/骨骼推导（叉口 t、首个暴露索引、控制点位置分布、取整钳位规则）被两处以上消费，**必须**抽成具名纯函数单点定义（如 `splitParentMainIndex`、`tipWidthSideControlTs`），消费方一律调用而非复制表达式；跨模块无法 import 时（视口/导出分层），在**每个**副本处注释写明「同规则同步点清单」并互相指向，改一处必须改全部。回归测试须含**跨消费方一致性断言**（例：断言视口 `firstBelow === ` 导出 `firstExposed`），而不是各自断言自己的值。宁可让不变式**构造性成立**（如按本侧 fork 分布控制点），也不要靠守卫事后过滤——守卫只作安全网。
- **创作空间与物化空间不得混用**（0.2.120 教训）：`bone.tip` 一类「rest + delta」结构，视口所画是**物化结果**（`materializeTipChain` 的 `shown[i] = rest[i] + (points[i] − restPoints[i])`），而 `authored.points` 是**旧** rest 基准下的陈旧绝对坐标。**任何读取绝对位置的编辑路径（拖拽、笔刷、gizmo、求解器）一律从物化链取值**（`splitTipForSegment`/`materializeTipChain` 的 `points`），写回时才重基准 `restPoints`；直接读 `authored.points` 再重基准 = 销毁 delta（症状是「一动就跳回原位」，跳回量恰等于 rest 位移）。新增此类结构时在定义处注释标明每个字段所属空间，并加**往返恒等**测试 + **负向对照**（按旧方式取种子，断言偏差恰等于 rest 位移），让测试自解释所守的回归。
- **验收脚本与真实存档解耦**（0.2.117/0.2.119 各误报过一次）：`scripts/verify-*.mjs` **禁止**写死来自用户存档的现场值（段数、暴露数、关节名、顶点数）——用户用 UI 编辑存档后会把正确行为报成代码回归。改为「按被测的同一公式从存档现场推导 + 一条不依赖具体档的交叉校验（单调性/不变式）」；可从代码常量推导的期望值一律引用常量（如控制点数 = `TIP_WIDTH_CONTROL_POINTS + 1`），不写字面量。真实 .ahs 路径只能作**可覆盖的默认参数**并在缺失时清晰跳过（非报错）。**排查口径**：真实档验收数量下降时，**先怀疑存档被编辑，再怀疑代码**（脚本直接读 .ahs、不经被改代码时尤其如此）。
- **修 bug 不夹带设计变更**（0.2.118→0.2.123 教训，已让同一处绕两轮）：修复 bug 时若顺手改动了**用户可见的编辑手感、控制点布局、数量或交互语义**，那不再是 bug 修复而是**设计变更**，必须单独提出并确认，不得夹带。0.2.118 把「消除隐藏活点」（对）和「控制点改成每侧各自等分」（错，导致两侧数量恒定、间距不一致）绑在一起提交，结果 bug 修好了但手感被改坏，只能再绕一轮回退设计。判据：若改动会让用户看到的**控制点个数/位置/间距**变化，或改变某个操作的手感，先确认再做；纯粹消除「不可达/不生效」的坏状态才算修复。
- **JS 改动标注**：所有 .js 修改/新增，需在 devlog「JS 改动标注」中标注与原有 JS 的差别/新增功能。
- **快捷键分区**：新增/修改的快捷键必须放在独立分区（自己的栏），不得改动原有快捷键说明；若与原有快捷键冲突或被代替，需标暗红并指向代替按键。
- **语言支持**：新增说明/文案需要同步添加现有语言支持（EN / JA / ZH）。**实测口径（0.2.134）**：本条在实践中只对**标签类**短文案严格成立 —— 长 `title=` tooltip 的词典覆盖率实测仅 **28/203（14%）**，四个 Trim 邻居（Left/Right Edge Trim、Tip Curve、Tip Loops）的 tooltip 就都不在 zh/ja 里。所以「某个 tooltip 没翻译」**是常态、不是回归**，不要当 bug 去修一小撮（那样只是把不一致换个位置）；要么整体补齐 175 条作为独立任务，要么保持现状。新增控件建议按 0.2.134 的半球区块做法把 label + tooltip 都补上（7 条 × zh/ja = 14/14），它现在**比邻居翻译得更全**。
- **版本号规范（2026-08 起）**：完整版本号格式 `0.1.5-Sintaka.0.2.<dailybuild>`。`0.1.5` 主版本**与上游保持对齐**（不随本地改动递增）；`Sintaka` 为本地 fork 标记；`0.2` 为分段版本号（功能迭代时更新）；末尾 dailybuild **可直接递增到 5 位数**（如 12 → 13 → … → 12345，分段版本号更新时清零）。**唯一真源** = `modules/core/app-config.js` 的 `APP_VERSION`，显示在顶栏与 Settings → Version；**本规范内不写任何具体版本号**（历史上这里写死过两个不同的「当前」值；0.2.129 又发现「当前 0.2.121」已落后 8 个版本 —— 就写在这条警告自身里，故彻底删除该括号,要查当前值请直接读 app-config.js）。
- **bump 清单（缺一即测试红）**：① `modules/core/app-config.js` 的 `APP_VERSION`；② `index.html` 入口缓存号**共 2 处**（`styles.css?v=` 与 `app.js?v=`，**两处必须同值**；具体值同样不在本规范复写 —— 用 `Select-String '\?v=' index.html` 读当前值；模块内 `?v=` 按 0.2.110 教训**定点刷新**，勿全局替换）；③ `tests/dom-contract.test.mjs` 冻结**断言 5 条**（APP_VERSION 1 条 + app.js 缓存号 3 条 + styles.css 缓存号 1 条）——注意 ×3/×1 指的是**测试里的断言条数**，不是 index.html 里的出现次数，可用 `Select-String '\?v=2026' tests/dom-contract.test.mjs` 定位。`package.json` 的 `version` 字段**刻意不随 bump 递增**（停在 0.2.63，仅 npm 元数据，不参与运行时与测试）；如需改动请同时更新本条。
- **子智能体委派（强制流程，2026-08 起）**：涉及代码修改的任务**默认派给子智能体执行**（即使只派 1 个也走此流程，**不绑定具体模型/产品名**——历史上写作「Codex 子智能体」，实际 0.2.117–0.2.121 均由 Opus/Sonnet 子智能体完成）。主进程（supervisor）负责深度调研、切分任务、合并审查与最终验证，无需用户每次手动提示。适用：并行调研（多 bug 根因分析、跨分支 diff 对比）、隔离改动（按文件/子系统边界切分）。规则：① 子任务**文件/子系统必须不相交**（共享文件由主进程独占，或串行交给同一个子智能体）；② **子智能体产出一律不可信直接采用**——主进程必须逐处复核实际文件状态、跑全量回归，对「跨文件同规则」类改动逐个同步点核对（子智能体报告里的数字也要抽验，实测出现过报告行数与实际不符）；③ 关键路径阻塞任务不委托；④ **子智能体中途失败时主进程直接接手完成**（有先例：0.2.117 死在半改文件上，重派风险更高）；⑤ 只读调研类任务连续失败 2 次即由主进程自己做。若需新增/调整此流程约定，直接写入本规范，勿等用户重复说明。

- **~~BOM 审计~~（0.2.131 起已作废，全仓库无 BOM、由 `tests/encoding-contract.test.mjs` 守住，见下方「编码统一」条；不要再对任何文件做「还原 BOM」，那会把该测试改红）**：本条仅保留仍有价值的**判 BOM 方法论**，供将来若需排查编码问题时使用——**必须**用 node 读 `Buffer` 判前三字节是否 `EF BB BF`；**禁止**用以下两种读法下结论，两者都会**吞掉 BOM 从而得出「无 BOM」的错误结论**：① `Get-Content -Encoding Byte`（读取时就丢 BOM，pwsh 5.1/7 皆如此）；② `[IO.File]::ReadAllText` 或任何 .NET 文本解码（解码时吞掉 BOM，`StartsWith('\uFEFF')` 判断恒为 false/true 皆不可信）。其余历史细节（pwsh 5.1 下 `>` 重定向把 `git show` 输出按 UTF-16 写盘凭空造出 `FF FE`、`write`/`edit` 工具会剥现存 BOM 等）已随「全仓库无 BOM」成为**不再有实际影响的旧观察**，不再是需要遵守的规则，此处不复述细节以免误导为仍需执行的步骤。

- **Git 调用约定（2026-08 起，勿再触发 Windows 弹窗）**：pwsh 里调用 git 必须把 `git` 放在**命令的第一个 token**（git 是信任前缀，整条命令不经过文件沙箱、无需审批）；**绝不**给 git 命令附加 `sandbox_permissions` 升级参数——升级重试会弹审批窗打断用户（本仓库 .git 写入在 git 作为首 token 时直接可用，无需升级）；报错由主进程自行消化并换方式重试（如先 `git -C <repo>` 或补 `git config --global --add safe.directory`），不要把错误弹给用户；仓库已配置 `core.autocrlf=true`（工作树 CRLF、入库 LF），不要手改行尾。**同一机制适用于全部信任前缀**（`git`/`node`/`npm`/`pnpm`）：信任命令必须是整条命令的**第一个 token**，不要写 `cd <dir>; node …` 或 `echo x; git …`——前置命令会让整条命令进沙箱、报 `Access is denied` + `[sandbox: file access denied]`，**看起来像环境损坏、其实是策略拒绝**（本轮实测踩过两次：`git show` 与 `node` 各一次）；改用工具的 `workdir` 参数传工作目录，同理**不要**给这类命令附加 `sandbox_permissions` 升级。提交信息含中文/多段时（**本条按 pwsh 7 实测更新，三步已可变一步**）：**首选直接 `git commit -m '…' -m '…'`，中文逐字节无损**（pwsh 7 默认 UTF-8；实测 `§`、`「」`、全角括号、em dash 全部原样入库，见提交 `0184e00`）。**必须用单引号** —— 实测双引号下 pwsh 会**静默吃掉反引号**、并把 `$PSVersionTable` 展开成 `System.Management.Automation.PSVersionHashTable`，而本仓库提交信息几乎每条都含 `` `代码` `` 与 `$`；单引号则字面保留。多段用多个 `-m`。**仅当正文本身含单引号**时，才回退到 `write` 写临时文件 + `git commit -F <file>`（提交后删除）。原先"必须写临时文件"的成因是 **pwsh 5.1**，pwsh 7 下已不成立；pwsh 仍不支持 heredoc `<<'EOF'`（会被解析成重定向报错），这一条不变。
